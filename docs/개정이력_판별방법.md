# 조·항 개정이력 판별 방법

`tb_law_atcl_amnd_hst`(TB_법령조개정이력), `tb_law_para_amnd_hst`(TB_법령항개정이력)가 **어떤 기준으로 채워지는지** 설명한다.
처음 이 시스템을 맡는 사람이 이 문서 하나로 이력 데이터를 읽고, 검증하고, 수정 시 주의점을 알 수 있도록 정리했다.

---

## 한 줄 요약

> 두 이력 테이블은 API에서 **수집하지 않는다.**
> 수집한 조·항 본문(bas 테이블)을 적재 단계(`load_csv.py`)에서 **서로 비교해 판별한 결과**를 넣는다.

law.go.kr API에는 "이 조가 언제 바뀌었다"를 조·항 단위로 바로 주는 데이터가 없다.
그래서 연혁(시행일자별 법령 버전)마다 조·항 본문을 저장해 두고, 버전끼리 비교해서 달라진 곳을 기록한다.

비유하면 **연혁마다 조문 사진을 찍어 두고(bas), 사진끼리 비교해 달라진 곳을 장부(이력 테이블)에 적는 것**이다.

---

## 1. 왜 조·항 단위인가

판결문은 법령을 인용할 때 "법령 전체의 연혁"이 아니라 **해당 조·항이 마지막으로 바뀐 시점의 연혁**을 기준으로 한다.
법령 하나가 개정되어도 대부분의 조는 그대로이므로, 조·항마다 독립적으로 "언제 바뀌었는지"를 관리해야 판결문 표기와 맞출 수 있다.

---

## 2. 비교 기준: 본문 해시

| 대상 | 해시 컬럼 | 해시 재료 |
|---|---|---|
| 조 | `tb_law_atcl_bas.atcl_ctxt_hsid` | 조문내용 + 항·호·목 전체 |
| 항 | `tb_law_para_bas.para_ctxt_hsid` | `<항>` 노드 안의 텍스트(항·호·목)만. 조 머리말은 제외 |

- 해시 = SHA-256(정규화한 본문)
- 정규화: **NFC → 공백·개행을 하나의 공백으로 → 앞뒤 공백 제거** (`common/utils.py` `normalize_text`)
- 공백·줄바꿈 차이만 있는 경우는 같은 본문으로 본다.
- **해시가 다르면 본문이 바뀐 것으로 판단한다.**
  본문 안의 `<개정 …>` 같은 태그는 판단 근거가 아니다. 기록할 때 개정일·개정유형을 채우는 데만 쓴다 (3.3 참고).

---

## 3. 기록되는 두 종류 (`amnd_rsn_cd_nm`)

### 3.1 amendment — 실제 개정

**같은 조(항)의 연혁들을 시간순으로 줄 세우고, 바로 앞 연혁과 본문 해시가 다르면 1건 기록한다.**

- 같은 조의 기준 키: `law_id + law_brch_no` (항은 `+ para_no`)
  - `law_id`(법령ID)는 법령의 모든 연혁에서 변하지 않는 키다.
  - `law_seq`(법령일련번호)는 개정 때마다 새로 부여되므로 그룹 키로 쓰지 않는다.
- 정렬: `enfc_ymd`(시행일자) → `prmlgt_no`(공포번호) → `entrvs_dvs_cd`(제개정구분) → `law_seq`
  (앞의 세 개는 색인쿼리 LEAD와 같은 순서. 마지막 `law_seq`는 동순위일 때 매번 같은 순서가 나오도록 붙인 것)

예시 — 어떤 법 제2조의 연혁이 아래와 같을 때

| 연혁(시행일) | 제2조 본문 | 해시 | 기록 |
|---|---|---|---|
| 2020-01-01 | "가"란 가를 뜻한다. | A | 없음 (첫 등장) |
| 2022-01-01 | "가"란 가를 말한다. <개정 2022.1.1> | B | **amendment: 2020 → 2022** |
| 2024-01-01 | "가"란 가를 말한다. <개정 2022.1.1> | B | 없음 (직전과 같음) |

- **첫 등장**(직전 연혁 없음)은 기록하지 않는다. bas 테이블에 이미 보이기 때문이다.
- 중간 연혁에 그 조가 없으면 조가 있는 연혁끼리 비교한다 (예: 2020 있음 → 2022 없음 → 2024 있음이면 2020↔2024).
- 같은 연혁의 다른 조들은 각각 독립적으로 비교된다. 법령이 개정되어도 바뀐 조만 기록된다.

### 3.2 anomaly — API 데이터 이상

**같은 연혁·같은 조(같은 PK)인데, 이번에 받은 본문 해시가 DB에 저장된 해시와 다르면 기록한다.**

- 법이 개정된 것이 아니라 API가 같은 버전을 다르게 내려준 경우다.
- 그래서 직전과 이번이 같은 키다: `prev_law_enfc_id = law_enfc_id`, `prev_enfc_ymd = enfc_ymd`
- bas를 덮어쓰기 **전에** 비교해야 하므로 적재 순서상 가장 먼저 수행한다.

### 3.3 개정일(`amnd_ymd`)과 개정유형(`amnd_typ_nm`)

이번 연혁의 본문에 들어 있는 인라인 태그에서 뽑는다 (`common/utils.py` `extract_amnd_info`).

- 대상: 조문내용·항·호·목의 `<개정 …>`, `<신설 …>`, `[전문개정 …]`, `제8조 삭제 <2009.3.18>` 등
  + `<조문참고자료>`의 `[본조신설 …]`, `[제목개정 …]`
- **가장 최근 날짜**를 `amnd_ymd`로 쓴다.
  예: `<개정 2008.2.29, 2013.3.23, 2025.10.1>` → `20251001`
- 그 날짜 태그의 유형을 `amnd_typ_nm`으로 쓴다: 전문개정 / 신설 / 삭제 / 이동 / 개정 / 제목개정
  - 같은 날짜에 여러 태그가 있으면 우선순위: 전문개정 > 신설 > 삭제 > 이동 > 개정 > 제목개정
- `[시행일: …]` 태그와 유형 키워드가 없는 날짜는 무시한다.
- 태그가 하나도 없으면 빈 값이다 (제정 이후 바뀐 적 없는 조).

> **주의 — 개정일 ≠ 시행일.** `amnd_ymd`는 공포·개정일이고, `enfc_ymd`는 시행일이다.
> 예: 2025.10.1 개정, 2026.1.2 시행. 두 값은 별도로 관리한다.
>
> **주의 — "전문개정 YYYY.M.D"는 마지막 전면개정일일 뿐**, 최신 변경일이 아니다.
> 그 뒤의 부분개정은 `<개정 …>` 태그로만 나타나므로, 가장 최근 날짜를 고르는 방식으로 처리한다.

## 4. 컬럼 설명

조 이력(`tb_law_atcl_amnd_hst`) 기준. 항 이력은 `para_no`, `prev_para_no`가 추가된 같은 구조다.

| 컬럼 | 의미 | amendment | anomaly |
|---|---|---|---|
| `law_atcl_hsid` (PK) | 이력 1건을 식별하는 해시 (4.1) | | |
| `law_enfc_id` | 이번 연혁 (법령일련번호+시행일자) | 이번 연혁 | 해당 연혁 |
| `prev_law_enfc_id` | 직전 연혁 | 바로 앞 연혁 | 이번과 같음 |
| `law_brch_no` / `prev_law_brch_no` | 조번호 4자리 + 가지번호 3자리 | 같음 | 같음 |
| `law_id` | 법령ID | | |
| `law_seq` / `prev_law_seq` | 이번 / 직전 법령일련번호 | | |
| `enfc_ymd` / `prev_enfc_ymd` | 이번 / 직전 시행일자 | 서로 다름 | 같음 |
| `amnd_ymd` | 개정일 (3.3) | | |
| `amnd_typ_nm` | 개정유형 (3.3) | | |
| `amnd_rsn_cd_nm` | `amendment` / `anomaly` | | |
| `detected_dt` | 적재를 실행한 시각 (DB `now()`) | | |

### 4.1 이력 PK 해시 (`law_atcl_hsid`, `law_para_hsid`)

```
조: sha256( law_id | law_brch_no | law_enfc_id | prev_law_enfc_id | amnd_rsn_cd_nm | atcl_ctxt_hsid )
항: sha256( law_id | law_brch_no | para_no | law_enfc_id | prev_law_enfc_id | amnd_rsn_cd_nm | para_ctxt_hsid )
```

- 본문 해시만으로 PK를 만들면 충돌한다.
  - 다른 법령의 같은 문구 (예: "제5조 삭제 <2010.1.1>") → 두 번째 법령 이력이 유실됨
  - 같은 조가 A → B → A로 원복 → 원복 이력이 유실됨
- 그래서 "어느 법령·어느 조·어느 연혁 쌍·어떤 본문"인지를 모두 재료로 쓴다.
- 이 PK는 **같은 사건을 두 번 넣지 않기 위한 식별자**이고, 변경 감지 로직이 아니다. 감지는 2절의 본문 해시 비교로 한다.

## 5. 언제, 어떤 순서로 만들어지나

적재(`python main.py load` / `all` / `incr`) 한 번은 **하나의 트랜잭션**이다. 중간에 실패하면 전체 ROLLBACK된다.

```
1. CSV → 임시테이블
2. anomaly 판별   : 임시테이블(이번 수집) vs DB bas(지난 수집)   ← bas를 바꾸기 전에
3. bas 반영       : full = TRUNCATE 후 insert / incr = UPSERT
4. amendment 판별 : bas 전체에서 같은 조(항)의 인접 연혁끼리 비교
5. 수집 실패 기록 : tb_law_clct_fail_hst
6. 이번에 새로 들어간 이력을 logs/{실행일}/{full|incr}/load_hst_*.log 에 건별 기록
```

- 이력 insert는 `ON CONFLICT DO NOTHING`이다.
  매번 전체 연혁 쌍을 다시 계산하지만, 이미 있는 사건(같은 PK 해시)은 무시되고 **새로 생긴 쌍만** 들어간다.
  따라서 같은 CSV로 다시 적재해도 이력이 중복되지 않는다.
- 두 이력 테이블은 **TRUNCATE하지 않는다** (append-only). 토요일 전체 수집 때 비우는 것은 bas 3종뿐이다.

| 상황 | amendment | anomaly |
|---|---|---|
| **최초 적재** | 전체 연혁의 모든 인접 쌍이 한꺼번에 들어감 (의도된 동작) | 0건 (비교할 DB 값이 없음) |
| **증분 수집 (일~금)** | 새로 들어온 연혁 ↔ DB의 직전 연혁 | 거의 없음 (본문이 안 바뀐 법령은 조회 대상이 아님) |
| **전체 수집 (토요일)** | 새로 생긴 쌍만 | 여기서 감지됨 |

> **주의 — `detected_dt`는 실제 개정 시점이 아니다.** 최초 적재 때 들어간 이력은 모두 최초 실행 시각을 가진다.
> 실제 개정·시행 시점은 `amnd_ymd`, `enfc_ymd`로 판단한다.

## 6. 확인용 쿼리

```sql
-- 특정 법령의 조 개정이력 (시간순)
SELECT law_brch_no, prev_enfc_ymd, enfc_ymd, amnd_ymd, amnd_typ_nm, amnd_rsn_cd_nm, detected_dt
FROM tb_law_atcl_amnd_hst
WHERE law_id = '010593'
ORDER BY law_brch_no, enfc_ymd;

-- 특정 조의 이력과 그때의 본문을 함께
SELECT h.prev_enfc_ymd, h.enfc_ymd, h.amnd_ymd, h.amnd_typ_nm, a.atcl_ctxt
FROM tb_law_atcl_amnd_hst h
JOIN tb_law_atcl_bas a ON a.law_enfc_id = h.law_enfc_id AND a.law_brch_no = h.law_brch_no
WHERE h.law_id = '010593' AND h.law_brch_no = '0004000'
ORDER BY h.enfc_ymd;

-- 구분별 건수
SELECT amnd_rsn_cd_nm, count(*) FROM tb_law_atcl_amnd_hst GROUP BY 1;

-- 최근 감지된 anomaly
SELECT * FROM tb_law_atcl_amnd_hst WHERE amnd_rsn_cd_nm = 'anomaly' ORDER BY detected_dt DESC LIMIT 50;
```

적재 한 번에서 새로 들어간 이력은 `logs/{실행일}/{full|incr}/load_hst_*.log`(탭 구분, 엑셀로 열기 가능)에서도 볼 수 있다.

## 7. 알려진 한계

| 한계 | 설명 |
|---|---|
| 조 번호 이동 | 제10조가 제12조로 옮겨가면 서로 다른 조로 보여 이어서 추적되지 않는다. 전부개정으로 조 번호 체계가 통째로 바뀌는 경우도 같다. |
| anomaly 뒤 이력 중복처럼 보임 | anomaly가 생기면 같은 연혁 쌍(예: 2020→2022)에 대한 amendment가 바뀌기 전 해시와 바뀐 후 해시로 2건 남는다. PK에 본문 해시가 들어가는 설계상 동작이다. |
| 중간 연혁이 늦게 들어오는 경우 | 2020→2024로 기록된 뒤 2022 연혁이 추가되면 2020→2022, 2022→2024가 새로 들어가고 기존 2020→2024도 남는다 (append-only). |
| 같은 값으로 반복되는 anomaly | X→Y, 다음 수집 Y→X, 또 X→Y처럼 반복되면 세 번째(X→Y)는 첫 번째와 PK 해시가 같아 기록되지 않는다. |
| `atcl_chg_yn`(API 조변경여부) | 감지 근거로 쓰지 않고 원문 그대로 저장만 한다. 바뀌지 않은 조에도 법령 단위 값이 찍혀 있어 조 단위 판단에 쓸 수 없다. |

## 8. 수정 시 반드시 지킬 것

**해시 규칙은 운영 적재 시작 후 바꾸면 안 된다.**
아래 중 하나라도 바뀌면 같은 본문이 다른 해시로 계산되어, 전 조·항이 amendment/anomaly로 오탐되고 이미 있는 이력이 중복으로 쌓인다.

- 본문 해시 재료: 조·항 본문 구성과 순서 (`crawl/law_detail.py`), `get_tag`의 공백 정리 (`common/xml_parser.py`)
- 정규화 함수 `normalize_text`, SHA-256·UTF-8 (`common/utils.py`)
- 이력 PK 해시의 재료 순서, 구분자 `|`, NULL → '' 처리 (`db/law_sql.py` `_hsid`)

불가피하게 바꿔야 하면 이력 테이블 백업 → 재생성(전체 다시 계산)을 전제로 별도 작업으로 진행한다.
